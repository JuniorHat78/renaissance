1. Every phase ships its own tests and must pass the FULL suite + visual before commit.
2. Internal links/assets stay RELATIVE. Anything new is verified under /renaissance/.

4. Manual smoke before commit; push to main per phase.
5. "Magical under the hood": invisible when it works, graceful when it doesn't,
     never naggy, always reduced-motion / touch / keyboard aware.

PHASE 10 — CROSS-BROWSER REGRESSION: CHROMIUM + FIREFOX + WEBKIT  [M]
================================================================================
GOAL  Run the functional regression suite on all three engines so behaviour is
      verified on Chrome, Firefox, and Safari's engine.

WHY   We use Clipboard API, View Transitions, color-mix, backdrop-filter,
      ::-moz-selection, matchMedia(pointer/reduced-motion) — all have per-engine
      quirks. WebKit especially differs on clipboard + transitions.

SCOPE
  - Centralize browser launch in a tiny test harness helper so every regression
    file can run under {chromium, firefox, webkit} instead of hardcoding chromium.
  - npm scripts: test:regression:firefox, test:regression:webkit (or a --browser flag).
  - ci.yml: matrix over browser; install with `npx playwright install --with-deps
    chromium firefox webkit`.
  - Triage real cross-engine failures (likely: clipboard permissions model in
    WebKit/Firefox; View Transitions absent in Firefox/WebKit — already opt-in so
    should degrade; backdrop-filter rendering).

HONEST CAVEATS (read before committing to this)
  - Playwright WebKit ~= Safari's engine, but it is NOT real iOS/macOS Safari.
    True device parity needs a real Mac/iPhone or a paid grid (BrowserStack/
    Sauce). WebKit-via-Playwright catches ~90% and is the right first step;
    real-Safari grid is DECLINED (see Q1) — WebKit matrix is the agreed bar.
  - Cross-browser VISUAL pixel diffs are notoriously flaky (font hinting, sub-pixel
    AA differ per engine/OS). So: cross-browser = FUNCTIONAL regression only.
    Visual screenshot diffing stays Chromium-only. Do not chase cross-engine pixels.

TESTS  Full regression suite passes on all three engines in CI matrix.
RISK   Medium. Expect to fix 1-3 genuine WebKit/Firefox behaviours. That is the
       point — those are real users.
TOUCHES  scripts/tests/* (harness), package.json, ci.yml

PHASE 12 — LIGHTHOUSE AS A MEASURING STICK (NON-GATING)  [M]
================================================================================
GOAL  Keep Lighthouse as an informative measuring stick that NEVER fails a PR on
      its own. It only raises a loud, human-readable flag when a PR moves the
      score DRASTICALLY, so you can choose to reverse. You stay in control.

WHY   (Your call, and the right one.) CI-runner Lighthouse is noisy — cold
      runners, network jitter, GC pauses swing scores +/- several points run to
      run. A hard gate on a "magical" site just produces flaky red PRs everyone
      learns to ignore. We want signal, not a tripwire.

SCOPE
  - Keep ci:lighthouse NON-BLOCKING (warning-only) as it is today. No build ever
    fails because of a Lighthouse number.
  - Commit a baseline snapshot (qa/lighthouse/baseline.json) of current scores +
    key metrics (LCP, CLS, TBT, total weight).
  - On each PR, run Lighthouse a few times and take the MEDIAN (kills single-run
    noise), then DIFF against baseline.
  - "Drastic" = a tunable delta only (e.g. any category drops >= 8 pts vs
    baseline, or LCP/CLS worsens past a set margin). Default thresholds generous;
    easy to tune in one config file.
  - If drastic: post a clear PR comment ("perf 97 -> 86 (-11) on /section.html —
    intended?") and emit a ::warning. Visible, decision-prompting, NEVER red.
  - If a regression is intentional, you bump the baseline in the same PR; that
    self-documents the trade in git history.
  - Routine small drift: silent. Improvements: optionally note them, never nag.

TESTS  A unit test on the diff logic: given baseline + sample run, it flags a
       drastic drop and stays quiet on noise-level drift. The Lighthouse run
       itself stays warning-only in CI.
RISK   Low — it cannot fail a build by design. Only real work is the median+diff
       harness and picking sane default deltas.
TOUCHES  scripts/ci/lighthouse-warning-runner.js, qa/lighthouse/baseline.json (new),
         lighthouse delta config (new), ci.yml (PR-comment step), scripts/tests/

PHASE 14 — OFFLINE READING / PWA  [L]  (bigger swing)  [CONFIRMED: go all the way]
================================================================================
GOAL  A reading site that survives a tunnel or a flight. Open an essay, lose
      signal, keep reading. Full offline — not just an installable shell.

WHY   The single most on-brand "magical" feature for a long-form reader.

SCOPE
  - manifest.webmanifest (name, icons, theme-color matching the paper palette).
  - Service worker: cache the app shell + the essay/section content the reader is
    actively in; stale-while-revalidate for content, cache-first for shell.
  - A quiet "available offline" indicator once a section is cached.
  - Update strategy: versioned cache, skipWaiting + a gentle "new version" nudge
    so readers never get stale content silently.

HONEST CAVEATS
  - Service worker SCOPE must be /renaissance/ (subpath again — same trap, new
    surface). Register with the correct scope or it silently no-ops.
  - file:// (the embedded-data fallback path) has no service workers — must
    degrade cleanly; SW is a pure enhancement.
  - Caching can serve stale essays; the version/update strategy is the hard part,
    not the caching itself.

TESTS  Playwright offline test: load section, go offline, navigate within cached
       content, assert it still renders; assert SW scope; assert update flow.
RISK   High-ish (most moving parts). Strictly additive; guard behind feature check.
TOUCHES  manifest.webmanifest (new), sw.js (new), registration shim, *.html, tests

PHASE 15 — BROADER A11Y & FOCUS-MANAGEMENT PASS  [M]  (taste)
================================================================================
GOAL  Beyond axe's automated checks: the things only a human walk catches.

WHY   Automated audits (Phase 11) catch ~40% of real a11y issues. This is the
      rest: keyboard journeys, focus choreography, screen-reader narrative.

SCOPE
  - Keyboard-only walk of every page: search controls, pagination, the copy chip,
    hover-preview parity (already has focus support — verify it announces).
  - Focus management across in-page navigation (where does focus land after a
    search anchor scroll? after opening a section?).
  - Screen-reader pass (VoiceOver/NVDA) of the reader: heading structure, the
    reading-progress bar's aria-hidden, live-region etiquette for toasts/hints.
  - Honour-the-narrative fixes only; no churn for its own sake.

TESTS  Targeted Playwright keyboard-journey assertions; manual SR notes recorded.
RISK   Medium. Some findings are judgment calls; surface them, don't auto-decide.
TOUCHES  HTML/CSS/JS as findings dictate; scripts/tests/
